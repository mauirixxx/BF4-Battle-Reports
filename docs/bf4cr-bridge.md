# BF4CR -> BF4BR native import bridge (2026-11-16)

The Python bridge in `tools/bf4cr_bridge.py` accepts BF4CR flattened player JSON as NDJSON on stdin, supports validation-only by default, and writes to BF4BR native `servers`, `battle_reports`, `players`, `report_players`, `battle_report_details` on `--execute`.

Input from `rnt-02` is generated by `/opt/bf4cr-export/export_year_ndjson.py YEAR` from the pre-existing `/tank/bf4cr-export/YEAR` files. 2013 produced 6,127 source player rows; native import processed 6,127 records and produced 6,000 synthetic generic reports. One of these is timestamped outside 2013, so preserve source timestamps. The source file export is not the full source database: only rows already exported to files.

Every synthetic report includes `bf4crImport.partialRoster=true`; recovered player records include `bf4crRaw` preserving all source fields. Existing native Battlelog JSON is never overwritten. No detail job is marked done, because flattened BF4CR records are not complete Battlelog player responses. Normal website archive and scoreboard use the existing `battle_report_details` format.

The existing PostgreSQL `bf4cr_bridge` role is allowed by `/etc/postgresql/18/main/pg_hba.conf` only from `192.168.200.71/32`, but has no password set. A temporary private-network HTTP transfer restricted to `192.168.200.49` was used for the 2013 source file. No continuous direct PostgreSQL streaming has been activated.

Validation: `python tools/bf4cr_bridge.py < YEAR-import.ndjson`; production: `runuser -u postgres -- /opt/bf4br-external-api/.venv/bin/python tools/bf4cr_bridge.py --execute < YEAR-import.ndjson`.

Before bulk continuation: establish authenticated source-to-destination bridge, inspect native collector queue semantics so synthetic partial reports are not mistakenly considered complete, verify year-by-year source export completeness, and test existing Battlelog report merging. Do not infer that a partial roster is complete or that BF4CR flattened statistics satisfy native detail enrichment.

## Direct database proof of concept

On 2026-11-16, `rnt-02:/opt/bf4cr-export/stream_db_once.py` streamed decompressed JSON directly from `bf4cr_reports.public.raw_reports` via an indexed `report_id` range. It served a single restricted private-network HTTP request to `reports` (192.168.200.49). The receiving command piped curl stdout directly into `tools/bf4cr_bridge.py --execute`, using local PostgreSQL peer authentication. A one-row Fuimus13 test and a 1,000-row bounded range both succeeded; the latter had 1,000/1,000 imported and zero reported decode errors. No intermediary JSON files were created.

This is a proof of concept, NOT yet a resumable production-scale importer. The temporary HTTP stream is unencrypted and must remain restricted to the private network. Its source process logs decode failures but does not yet propagate them to the receiver; a failed or truncated HTTP stream must not be treated as a completed range. For full-scale use, add authenticated transport, durable source cursor, batch-level acknowledgments, and error accounting. Report IDs are text in BF4CR; the source index can support lexical ranges only if fixed-length ID ordering is verified. The dedicated `bf4cr_bridge` role now has a password set, but the remote login has not yet been tested and native table INSERT grants are still absent.

## Resumable import (tested)

`migrations/0011_bf4cr_import_checkpoint.sql` adds `bf4cr_import_checkpoint` (one cursor per source) and `bf4cr_import_rejected` (malformed source payloads and error messages). Both are separate from native BF4BR report/enrichment tables; no second historical report archive is created.

Source: `rnt-02:/opt/bf4cr-export/stream_batch_once.py` is a **single-request proof-of-concept HTTP server** bound to 192.168.200.71:18715 and restricted to requests from reports (192.168.200.49). It queries BF4CR PostgreSQL directly via local peer auth and streams all player rows belonging to the next N distinct report IDs, in **lexical text order**, matching the source's report_id text btree. Each row is emitted as NDJSON with report_id and decoded JSON. A terminal footer carries SHA-256 of the exact NDJSON row bytes, row count, last report ID, previous cursor, and source completion/error flags. Source has no persistent process/service yet; it exits after one request.

Receiver: `tools/bf4cr_resume.py --reports 10` (run as postgres using the BF4BR venv). It locks a source checkpoint row, imports native report/player/scoreboard records, quarantines malformed source payloads in `bf4cr_import_rejected`, validates the footer and checksum, and commits checkpoint and records atomically. A missing footer, mismatched count/hash, source query error, or destination database exception rolls back the whole batch. `--fail-after N` injects a test-only failure for rollback verification; never use in production.

Tests: 10 report IDs -> 163 rows committed; injected failure after five rows -> transaction rollback and unchanged cursor; retry encountered one source payload missing personaName, which was preserved in reject table; following retry -> 128 rows processed, 127 valid and one rejected, checkpoint advanced. Last verified checkpoint `1000000757990687296`, 291 source rows processed, 2 batches, 1 rejected.

**Not ready for unattended 815M-row processing:** source HTTP is temporary and unencrypted; implement authenticated transport and persistent service, add per-batch retries and operational logs, handle corrupted base64/gzip at source with durable quarantine rather than failing the entire batch, review row-level DB performance/storage, and ensure normal collector semantics for partial reports. PostgreSQL `bf4cr_bridge` password and pg_hba rule are configured but remote role is not used by this proof-of-concept.

## Operator-controlled year-by-year rollout decision

User explicitly requested one historical year at a time, with a manual review of database size and free filesystem space before proceeding to the next year. Do not create a continuous all-years automation. Added `tools/bf4cr_storage_status.py` (run under local postgres role) for a read-only snapshot of database bytes, filesystem capacity, synthetic report count, rejects and checkpoints. Verified 44 GB BF4BR DB and ~910 GiB filesystem free on reports.

**Year boundary prerequisite:** BF4CR `raw_reports.created_at_raw` is text containing Unix seconds and lacks a date index; `report_id` is also text, with a btree index and lexical ordering. Do not label lexical report-id ranges as complete calendar years. Need to implement and verify a correct year-scoped indexed retrieval strategy (or a deliberate bounded source scan/index build) before initiating 2013 full-source import. Existing global source checkpoint is at 1000000757990687296 (lexical order) after 291 rows; preserve it and do not reuse it as a calendar-year cursor. Use separate per-year checkpoints only after establishing reliable year filters. Review database growth and free space after each year, and require user approval before starting the next year.

## Calendar-year selection: verified strategy, source index build underway

On rnt-02, BF4CR `public.raw_reports` has ~814,269,248 estimated rows, 722 GB heap, 11 GB existing indexes. `report_id` is NOT a reliable exact calendar-year cursor: a sampled ordered set had multiple timestamp reversals. `created_at_raw` is text representing Unix seconds, and 800 sampled values were all ten digits. A year can be selected using an exact half-open UTC Unix-second range (e.g. 2014: `created_at_raw >= '1388534400' AND created_at_raw < '1420070400'`), with validation of decoded payload `createdAt` against the source timestamp. This is accurate for rows whose source timestamp is valid; malformed/outlier timestamps require separate audit/quarantine.

The previous date-filter query planned a sequential scan of the 722 GB table. On 2026-11-16/17 we started `CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_bf4cr_created_report ON public.raw_reports (created_at_raw, report_id)` on rnt-02. **Index build is not yet complete; do not start year import until `pg_index.indisvalid` and `indisready` are true and the year-filter query plan is verified.** PostgreSQL index progress is available via `pg_stat_progress_create_index`. Source has ~17 TB free on /tank at start.

Year-by-year import must use a NEW year-specific checkpoint and source endpoint with `(created_at_raw, report_id)` keyset pagination, including all duplicate player rows for a given report group. Do not reuse the existing lexical global cursor. Year import should stop at each year boundary and report target database size and filesystem free space for user approval. Preserve all existing BF4BR records and rejected payloads.

## 2018 live year-specific import (2026-11-18)

The 2018 importer is `tools/bf4cr_import_2018.py`, driven by `tools/bf4cr_run_2018.py`, and reads the private-network source endpoint on rnt-02 (`/opt/bf4cr-export/stream_2018_server.py`, port 18721). The importer verifies ordered keys, year bounds, payload identifiers, row count, SHA-256 footer, and commits native rows and the `bf4cr-2018` checkpoint atomically. It stops at the 2018 boundary; it does not automatically proceed to 2019. The runner checks for at least 150 GiB free before each batch.

On 2026-11-18, a transient PostgreSQL lock timeout while inserting into the `players` index rolled back one batch; checkpoint remained at 11,583,421 rows / 10,130 batches. The runner now retries **only** lock-timeout failures up to six attempts with 5/10/20/30/60-second delays; other errors still stop the run. Restart from the existing checkpoint successfully committed 1,035 additional source rows (11,584,456 / 10,131 batches). The running process was restarted on `reports`; monitor `/var/tmp/bf4cr-2018-import.log`.

The repository currently preserves the tested 2018 scripts rather than refactoring the active import. Future work: consolidate the year-specific importer/runner/source-streamer into parameterized tools with independent year checkpoints, tests, and explicit per-year approval; preserve the running 2018 behavior until completion. The source streamer is presently deployed on rnt-02 and must be separately archived in the repository.
