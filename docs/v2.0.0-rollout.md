# BF4BR v2.0.0 rollout notes (work in progress)

**Release status: NOT READY TO TAG OR DEPLOY.**

## Completed
- Migration `0007_player_detail_enrichment.sql` committed to GitHub and applied to the live `bf4_battle_reports` database on the reports host (2026-11-07 UTC).
- Added three additive tables for report scheduling, persona job leases, and raw persona JSON. Created newest-first, claim, expiry, and single-active-report indexes. Granted the existing collector role access.
- Tested DDL in a rollback transaction before applying. Verified all three tables exist afterward and existing generic reports remain.
- Updated `docs/database-schema-reference.md` and `docs/player-detail-enrichment-plan.md`.

- Database-backed report roster seeding, global report activation, seven-worker persona claim/lease fencing, successful JSON archival, report-level atomic completion.
- Newest-first scheduling with current-report completion and deferred retry handling for permanently unavailable personas.
- Preserve node-wide request pacing and 429 cooldown; ensure player-detail requests share the existing per-node request budget.
- Add dedicated detail-worker role to coordinator, supervisor, deployment controls, monitoring and updater; preserve daily generic collection.

- One controlled end-to-end report canary, then a staged seven-node rollout with rollback plan and health verification.

## Operational warning
The schema is present but **no player-detail collectors are enabled**. Do not manually change historical node assignments to a nonexistent worker type. Do not publish a v2.0.0 release until all items above are tested and verified.

## Rolling pipeline revision
- Migration `0008_rolling_detail_pipeline.sql` was applied on production; verified replacement active-order index and zero enrichment jobs.
- The single-active-report barrier from `0007` is obsolete. Up to two reports may be active simultaneously by default. A new report opens once all immediately eligible players in active reports are claimed, while existing leases continue.
- Newest active report takes priority for fresh player claims. Each active report is settled independently, with full raw-response verification before completion.
- Updated `bf4br/detail_queue.py` and `bf4br/detail_worker.py` for rolling activation and settlement.
- The existing eight unit tests passed after the migration. **No PostgreSQL concurrency, lease-expiry, or multi-report integration tests have passed yet; supervisor activation and fleet deployment are still blocked.**

## Coordinated supervisor integration
- `bf4br/supervisor_assignment.py` now maps historical/rotating assignments to `bf4br.detail_worker` only when explicitly enabled.
- `bf4br/supervisor.py` requires both `BF4BR_COORDINATED=1` and `BF4BR_DETAIL_V2_ENABLED=1` to enable conversion. Without the new flag, the old assignment behavior remains.
- Existing supervisor drain-before-replacement process logic is reused; no production service flags have been changed.
- Twelve assignment/supervisor tests passed, including v2 role mapping, daily preservation, and paused/zero-worker behavior.
- **Outstanding**: true concurrent PostgreSQL claim and lease-expiry tests in a disposable database; scheduler/fleet-wide readiness gating; canary verification; no v2.0.0 tag or deployment authorized yet.
