# BF4BR v1.0.5 — daily UTC catch-up

**Release:** published 2026-11-04, tag `v1.0.5`, commit `df24fee`.

**Deployment status:** release published; automatic fleet upgrade and daily-worker activation must be verified separately. This document describes implemented release behavior, not a claim that the 3/7 allocation is already active.

## Purpose and allocation

Preserve the historical backfill while collecting newly observed BF4 player history on a daily UTC cadence. The intended allocation is three existing persona workers dedicated to daily collection (one per platform) and seven continuing historical backfill. No increase in total persona workers or per-worker request pacing is intended.

## Daily collection flow

1. The UTC importer identifies distinct observed platform/persona identities from BF4SW sessions overlapping the target day. Sessions crossing midnight are included; missing persona IDs are not invented.
2. The importer schedules identities in an independent daily queue with durable progress and retries.
3. The dedicated daily persona worker fetches Battlelog history for the day without overwriting historical backfill cursors.
4. Discovered reports are deduplicated against existing discoveries and prioritized for report processing, while historical report collection remains available.
5. The UTC timer and designated node configuration must be enabled separately from publishing the release.

The BF4SW source reflects monitored server sessions, not every possible Battlefield match. Late reports and upstream Battlelog failures may delay completion.

## Rollback

If the new release causes production problems, stop or drain affected workers and use the existing versioned release mechanism to return to the previous working version. Preserve database queue state and historical checkpoints; do not delete them as part of rollback.

## Prior design

The original design required separate daily queues, midnight-overlap handling, idempotency, and platform isolation. Those are represented in the v1.0.5 code and regression tests. Live deployment verification remains an operational check, not an additional development-test campaign.
